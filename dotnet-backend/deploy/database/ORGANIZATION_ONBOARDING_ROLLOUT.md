# Organisation onboarding defaults and lifecycle

OrganizationOnboarding:Types supports existing enum keys Hospital, Clinic and NursingHome (other established enum values are retained). Each type exposes RequireProfile, RequireTeam and RequireWhatsApp. Missing configuration preserves existing required profile/team/WhatsApp defaults. No bed count, ICU/surgery workflow, permission, module entitlement, financial policy or clinical grant follows from organization type. API registration/platform type changes validate known enums; type changes preserve history, completed onboarding and entitlement state.

GET/api/onboarding is read-only and returns existing flags, IsComplete from persisted tenant completion and RequiredSteps. A missing historical state is an unresolved projection, not inserted on GET. Mutation routes require current Settings.Edit. Profile/team steps verify stored active profile/colleague rather than accepting arbitrary completion booleans. Completion locks the tenant, checks active approved lifecycle/reviewer, rechecks required evidence, and commits state/tenant flag/protected operational audit atomically. Repeated completion retains the original completion timestamp. It never sets unverified steps true.

WhatsAppSettings currently has credentials/enabled flags but no durable provider verification record. MarkWhatsApp/required connection completion returns409 rather than treating credentials or historical boolean as proof. A deployment can explicitly configure RequireWhatsApp=false where communications is optional; no automatic policy relaxation is performed. Existing completed records are preserved.

New registration atomically commits tenant/user/profile/onboarding/role assignment/template metadata. It records submitted time. Platform lifecycle review records reviewer/start time and approval/rejection decision time/actor with existing request-key/audit transaction. Lifecycle/review calls do not create duplicate tenants. Pending/rejected/suspended applicants cannot stamp onboarding complete. Legacy review fields remain nullable; no historical reviewer is fabricated.

AddTenantLifecycleReviewEvidence is additive and unapplied. Runtime Tenants update grants narrow to onboarding flag/timezone/timestamp; login identity can select/insert tenants but cannot change lifecycle approval. Reviewed control-plane authority owns approval decisions. Protected migration/role/reviewer and provider-proof rehearsal remain activation gates. No test files, existing-data rewrite or provider sends occurred.
