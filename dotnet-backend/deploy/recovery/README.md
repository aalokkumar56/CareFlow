# Protected recovery and incident procedure

BE-009/BE-027 preparation, not an executed recovery exercise. Do not execute restore/rotation steps until the operator, protected backup, recoverable keys, isolated destination and accepted recovery targets are recorded. The current development database is not disposable. No recovery destination, retention duration or notification policy is selected by this document.

## Executable synthetic rehearsal

`Rehearse-Database.ps1` creates a fresh empty loopback-only PostgreSQL cluster under the supplied work root. It never reads application connection settings or opens an existing hospital database. Export the current EF migration SQL, then supply its path, `deploy/database/authority-boundaries.sql`, and a private temporary work root. PostgreSQL tools can be supplied with `-PostgreSqlBin`; an installation outside PATH is supported.

The tool applies migrations and authority SQL, repeats the grants, verifies actual control-plane clinical access denial and narrow session grants, creates one synthetic marker, archives/restores to a second new database and reconciles marker/history. It stops its helper and removes temporary plaintext connection password files; retained clusters, synthetic-only archive and hash evidence remain in a unique `synthetic-*` directory. Run from PowerShell with permission to launch the hidden helper. No normal API, worker or external provider is started. Synthetic archives are not clinical backups and contain no existing hospital records. This does not replace encrypted existing-data/object recovery, measured recovery targets or accountable acceptance below.

## Existing-data backup preparation

Record source instance/database identifiers, PostgreSQL major version, applied `__EFMigrationsHistory`, restricted runtime roles/policies, installed extensions and named authority connections without credential values. Record every file root: private document objects/version ledger, retained original clinical uploads, WhatsApp/relay media, protected audit state, and required configuration/key references. Repository source and migration files are not backups of database or file content.

Use the selected host's approved encrypted backup/PITR service or matching PostgreSQL tooling to take a protected database snapshot. Capture cluster role/grant definitions separately in the same protected envelope; they can contain credential material and must never be committed or printed. Private objects are immutable; retain all referenced versions, quarantine objects and legacy originals, with tenant/version/length/hash manifests. Do not delete unreferenced objects during backup. Coordinate a database snapshot with a retained object snapshot or pause document publication briefly so no referenced object is missing. Store encrypted copies under independently controlled access and approved retention. Record the recoverable encryption-key reference and prove that a separate authorized recovery identity can access it.

Document achieved snapshot/PITR time and lag; do not substitute proposed architecture RPO/RTO for measured results. Missing database tools, inaccessible keys, absent referenced files or unverified backup authenticity block recovery acceptance.

## Isolated restore

1. Verify absolute destination identifiers are different from the source and approved for protected clinical data. Create a new isolated database and distinct storage volumes; never drop/overwrite the source. Deny outbound provider/notification callbacks at the network boundary. Disable outbox processing and every scheduler/provider worker; configuration alone is insufficient when an existing worker has no disable switch. Do not start the normal API until this isolation is verified.
2. Verify backup authenticity, decrypt only inside the protected destination and restore using matching PostgreSQL tooling. Recreate approved roles/grants deliberately; do not reuse unrestricted source login privileges or expose credentials. Retain originals and restore private version ledgers, object bytes, quarantine/evidence, audit/idempotency/outbox state and required key references together.
3. Verify migration history, schema/constraints, restricted connection privileges, forced RLS and all authority paths. Reconcile per-table/per-tenant counts, missing parents, cross-tenant links and patient/visit/appointment coherence without dumping clinical rows into logs. Verify hash/length for referenced file versions and an authorized sample of legacy originals. Missing files/keys or unreviewed association anomalies fail acceptance; do not guess parents or discard rows.
4. Reconcile pending/failed outbox jobs and receipts with preserved event/dedupe IDs while workers remain stopped. Never replay provider sends as a recovery check. Prove one authorized recovery identity can inspect evidence and that unauthorized tenant/platform identities cannot read clinical rows/files.
5. Record elapsed restore time, recovered point, lost-data window, verification results, destination, operator/reviewer and gaps versus accepted targets. Keep the protected artifact references outside public logs/repository. Cleanup requires the destination owner's retention decision; this procedure does not authorize deleting the recovered copy or source data.

## Incident containment

The accountable operator records incident time/scope and restricts public ingress, affected provider egress and worker execution using the approved deployment controls. Preserve database snapshots, append-only clinical/operational audit, event receipts, object versions and protected logs before repair. Do not erase evidence, mutate signed history or move suspect objects into a public folder.

For credentials: revoke the affected persisted platform session or hospital refresh family; increment hospital user security revision for account compromise. Verify denial across every instance after additive session migrations are deployed. Rotate JWT signing keys and affected named database/provider credentials under the host's secret mechanism; coordinate all instances and verify old credentials fail. No unsupported token-key overlap/recovery grace is implied. Recoverability of encrypted data keys must be checked before replacing/removing a key reference.

For exposed files: close the exposure and retain original bytes/version/hash; verify private-root and download authorization on every instance. Quarantine downloads that lack approved clean scan evidence. For audit persistence failure: sensitive accesses must fail closed; preserve the outage interval and restore audit persistence before restoring affected access.

The selected country's accountable privacy/clinical owner assesses notifications and residual clinical risk. No jurisdiction, reporting deadline or legal conclusion is invented here. Recover through the protected restore procedure, reconcile ambiguous writes/provider effects, verify authority/access/audit, then have the recorded owner authorize resumption. Document a tabletop or isolated exercise for each scenario and its measured results; a runbook alone does not complete BE-027.
