# Backend request budgets

BE-014 source preparation; deployment-wide acceptance remains pending. No database migration is required by these controls.

The existing ASP.NET rate limiter combines network policies for login/registration/bootstrap with global minute and concurrency budgets. Verified JWT tenant/subject claims select independent authenticated quotas. Tenant selectors and forwarded IP headers never select quotas. Socket IP is used until an explicit trusted proxy configuration is approved; installing forwarding for all callers is prohibited. Platform traffic uses its actor plus socket-network scope.

Configuration under `RateLimiting`: ActorRequestsPerMinute (300), TenantRequestsPerMinute (1200), NetworkRequestsPerMinute (120), ActorConcurrency (8), TenantConcurrency (32), ExpensiveActorConcurrency (2), LoginAttemptsPerMinute (10), RegistrationAttemptsPerTenMinutes (3), BootstrapAttemptsPerTenMinutes (3), AccountAttemptsPerMinute (20). Values have source hard ceilings. Development/Testing may relax minute quotas; production ignores `RateLimiting:Relaxed`. Account attempts use a hash of normalized account plus hospital/platform scope, before password verification, independent of whether the account exists; minute windows expire without permanently disabling accounts.

Imports, form requests and AI endpoints have a separate actor concurrency budget. No quota queues requests. Rejections use safe 429 problems and Retry-After. These are **per-process** quotas: an approved edge/shared limiter is required before multiple replicas provide deployment-wide protection. This source does not claim distributed enforcement or invent a proxy/network allowlist. Verify legitimate shared-network traffic and limits under the selected replica count before activation.

`RequestLimits:JsonBytes` defaults to 1 MiB (hard maximum 8 MiB); `FormBytes` defaults to 11 MiB (maximum 32 MiB). Only the existing WhatsApp media-send and conversation media routes permit `MediaBytes`, default/maximum 101 MiB including multipart overhead; existing endpoint/service file caps still apply. Announced oversized bodies are rejected before reads. A counting request stream enforces actual bytes even without Content-Length and restores the original stream afterwards. Form values/headers are separately bounded. Request bodies and submitted credentials are never included in these controls' logs or rejection metadata.

Patient imports accept at most 5,000 total rows including the header and 128 columns. Excel materializes only the first sheet and checks rows/columns/cancellation before adding rows to its DataSet. CSV checks inside its transaction; exceeding a bound throws and rolls back every pending insert. Split larger imports into smaller files. Existing import parsing logs still require broader PHI-log remediation before release.

`RequestLimits:TimeoutSeconds` defaults to 180 seconds (allowed 10–600). ASP.NET cancels the request token and writes a safe 504 where transport permits. Cancellation is cooperative and cannot guarantee that an already committed write or external send was undone. Clients must verify current state after ambiguous responses; never automatically replay clinical writes without their approved idempotency contract. Existing queued-job/outbox semantics remain separate.

Verification: combined API build and nine transient in-memory size/account/actor/tenant checks passed on 7 October 2026. No test files, provider calls or existing database access were used. Chunked HTTP behavior through the selected proxy, legitimate pilot throughput, deployed replica quotas, cancelled-write reconciliation and a bounded endpoint inventory remain operational acceptance gates.
